# ADR 002: Admin sessions and catalog media

Status: accepted.

Admin authentication uses Argon2id (64 MiB memory, three iterations, one lane), verified on Node 24/Windows using the stable argon2 package. The interactive admin:create command prompts twice without echo and accepts 12–128 characters. Emails are normalized and unique. There is no default password, public registration, localStorage token or customer authentication.

Each login creates independent 256-bit opaque session and CSRF tokens. PostgreSQL stores only SHA-256 hashes. Both raw values live in HttpOnly, SameSite=Lax cookies scoped to /admin, with Secure in production and an absolute eight-hour lifetime. The server renders the CSRF cookie into forms only after verifying it against the session hash. All mutations validate it; multipart upload validates the first field before reading images. Login has a separate cookie/form CSRF challenge and an eight-attempt/15-minute per-IP limit. Foreign Origin headers are rejected. Helmet uses strict-origin-when-cross-origin so legitimate browser form submissions retain their origin. GET never mutates catalog state; last-seen session bookkeeping is the only read-side metadata update.

Disabled admins and expired/revoked sessions are rejected on every protected request. Logout deletes the session. Expired sessions are cleaned at login; dedicated maintenance and account recovery/MFA are deferred. One active admin status grants catalog administration; no vendor dashboard or customer roles are introduced.

Catalog owns persistence and validation. Admin routes render forms and call catalog services. Products receive the seeded LOKKA vendor automatically; writes and private previews verify ownership. Categories have active/hidden states, products draft/active/archived, variants active/inactive. The migration preserves old values by mapping non-active category/variant states to hidden/inactive. Category writes serialize using a transaction-level advisory lock to prevent concurrent hierarchy cycles. Slugs are generated only when blank; existing forms retain them independently of name changes. Operators should preserve established URLs; automatic slug history redirects are deferred.

Media is stored through CatalogImageStorage, currently LocalCatalogImageStorage. A future S3 adapter can replace persistence without changing catalog use cases. Images are decoded with sharp after byte-signature checks; JPEG/PNG/WebP only, static images only, 10 MiB/file, 40 megapixel decoded limit, five files/request and 20/product. Random UUID keys never contain user filenames. Regenerated WebP derivatives fit 400/800/1600 pixel bounds without enlargement, preserve aspect ratio and strip metadata. Source uploads are not retained. The official logo is outside this pipeline and is served byte-for-byte at its canonical URL.

Product row locks serialize primary-image writes; a partial unique index enforces at most one primary. Deletion promotes the next ordered image. Failed uploads compensate by removing saved files. DB deletion commits before filesystem deletion: a cleanup failure can leave an unreachable orphan and requires operational cleanup; it cannot leave a live DB row referencing deleted files. Uploaded directories must be writable only by the application/operator and must not contain attacker-controlled symlinks. Back up PostgreSQL and media together.

Public media lookup uses an indexed storage key and active-product/LOKKA join. Draft media requires authenticated /admin previews. Public image responses cache for five minutes; previously cached public images may remain visible until cache expiry after archival. The initial admin lists and sitemap target a small single-vendor catalog; pagination/segmentation for large administrative datasets is deferred.
